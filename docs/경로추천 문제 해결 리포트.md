# 경로 추천 문제 해결 리포트

작성일: 2026-09-17 · 대상 문서: [경로추천 문제 정의.md](경로추천%20문제%20정의.md) (09/14) · 작업 이력: [WORK.md](WORK.md)

## 1. 요약

RoadPulse의 AI 경로 추천은 09/14 시점에 **경로 통행시간을 예측하는 모델이 아니라**, OSRM 후보 경로에 교통량 증가율 패널티를 더해 순위만 매기는 휴리스틱이었다. 화면의 소요시간은 OSRM 자유속도 기준값이었고, 실제 통행시간과의 관계를 검증할 데이터도 없었다.

09/14~09/17 나흘 동안 다음을 완료했다.

| 단계 | 내용 | 결과 |
|---|---|---|
| 공간·방향 정합 | 서울시 서비스링크 5,341개의 선형을 국가 표준노드링크에서 복원하고, OSRM 경로를 링크에 길이 단위로 map-match | 링크 매칭률 58% → 85%, 반대 방향 혼입 0% |
| 경로 학습 데이터셋 | 후보 경로 × 출발 시각 단위, 실시간 피처 35개, 관측 속도 재구성 라벨, 누수 자동 검사 | 3,136행 · 1,680요청 · 누수 0행 |
| 경로 소요시간 모델 | XGBoost 회귀, OSRM 순서 베이스라인과 동일 holdout 비교 | Top-1 55.7% → **88.0%**, regret 271초 → **24초** |
| 새 경로 일반화 | 학습에 없는 OD 7쌍 holdout | Top-1 68.2% → **82.5%** |
| 서비스 연결 | 모델 ETA로 추천 순위, 자격 미달·오류 시 휴리스틱 fallback, 근거·품질 응답 | 실요청 검증 완료, 배포 대기 |

정의서 §9 완료 기준 11개 중 10개를 충족했고, 마지막 "기존 운영 방식 대비 개선"은 배포 후 온라인 라벨로 확인한다(§7).

## 2. 문제 정의 (09/14)

정의서 §3이 지적한 핵심 문제는 네 가지였다.

1. **학습 목표와 서비스 목표의 불일치** — 모델 정답은 측정지점의 시간당 차량 수, 사용자가 원하는 답은 경로의 통행시간과 후보 간 순위.
2. **공간 단위 불일치** — 측정지점(139개) 대 OSRM 도로 구간을 도로명 문자열로 연결. 표기 차이·동명 도로·터널/램프에서 매칭 실패.
3. **방향 정보 소실** — 상·하행 교통량을 합산해 반대 방향 정체가 내 경로 비용에 섞임.
4. **평가 지표 부재** — 교통량 RMSE만 있고, "실제 최적 경로를 골랐는가"를 잴 방법이 없음.

결론은 "교통량 예측 데이터셋을 고치는 것이 아니라, **경로 단위 데이터셋을 별도로 만들어** 경로 통행시간과 순위를 직접 학습·평가한다"였다.

## 3. 해결 과정

### 3.1 링크 선형 복원 (09/15)

서울시 속도 관측의 단위인 서비스링크에는 좌표가 없었다. TOPIS "2026-03 서울시 표준링크 매핑정보"(서비스링크→표준링크 1:N)와 국가교통정보센터 표준노드링크 shapefile(156만 링크, EPSG:5186)을 결합해 복원했다.

매핑표가 구성 표준링크를 일부만 담고 있어 세 단계 보정이 필요했다.

- 500m 이상 떨어진 표준링크 군집은 매핑 오류로 제외(206개)
- 매핑 링크 사이의 빈 구간을 서울 범위 표준링크 그래프(107,588개)에서 방향 최단경로로 보충(7,494개)
- 서울시 축·순번 정보로 이웃 서비스링크 사이를 보충해 양 끝 잘림 보정(6,452개, 경계는 절반 분할 근사)

결과: 5,341개 중 `complete` 4,667 / `partial` 394 / `unmapped` 229 / `missing` 51. 도로명 일치 97.3%, 이웃 링크 간격 ≤100m 3,966/4,014쌍. `road_segments`에 폴리라인·시종점·방위·품질 컬럼을 추가했다(007).

부수 발견: 서울시 `axis_direction`(상행/하행)은 도심 유입/유출과 무관(상행의 47%만 도심 방향)하므로 방향 판정에는 쓸 수 없고, **링크 방위와 진행 방위를 직접 비교**해야 한다.

### 3.2 OSRM 경로 → 링크 map-match (09/15~16)

1차 구현(다른 에이전트 작업)을 실제 데이터로 검토해 세 가지를 수정했다.

| 문제 | 수정 |
|---|---|
| 링크를 시·종점 직선으로만 표현 → 곡선 링크에서 60m 밖으로 벗어나 매칭 실패 | `geometry_json` 폴리라인 사용, 샘플점에 가장 가까운 선분의 방위 비교 |
| step 중간점 하나로 링크 하나만 매칭 → 1~2km step이 링크 2~4개에 걸침 | step 폴리라인을 100m 간격으로 샘플링해 링크 여러 개에 길이 배분 |
| 거리만으로 최근접 링크 선택 → 나란한 반대 방향 링크에 붙음 | 방위 일치(45°) 링크 우선, 반대 방향만 가까운 구간은 `opposite_m`으로 분리해 관측에 사용하지 않음 |

서울역→강남역 검증: 링크 매칭 58% → 85%, 매칭 링크 7 → 18개, 반대 방향 0%. 배포 후 실제 요청에서도 링크 매칭률 0.75~0.99, 방향 일치 0.88~1.0.

### 3.3 통행시간 라벨 재구성

실제 주행 기록이 없으므로 정의서 §5.2의 1차 대안대로 링크 관측으로 재구성한다.

- 1차 구현은 매칭 링크의 통행시간을 step 시간으로 **그대로 대체**해 1,935m step에 746m 링크의 86초가 들어가는 식으로 왜곡됐다(같은 경로가 OSRM 744초 / 1차 방식 1,235초 / 속도 스케일 1,522초).
- 수정: step에 배분된 링크 길이 × 해당 링크 관측 속도. 관측 없는 길이는 OSRM 시간을 길이 비례로 유지.
- 관측은 주행 중간 시각(출발 + OSRM/2) ±60분에서 선택. 관측 설명 길이 비율로 품질 등급(high ≥0.8 / medium ≥0.5 / low ≥0.3)을 매기고 **0.3 미만이면 라벨을 만들지 않는다**.

### 3.4 경로 학습 데이터셋 (09/16)

정의서 §5.2 스키마를 전부 구현했다. 한 행 = 한 후보 경로 × 한 출발 시각.

- **입력(35개)**: 출발 직전 링크 속도(평균·병목·통행시간 합·커버리지·관측 지연), 측정지점 교통량 lag, 매칭 링크 위 활성 돌발(유형별 건수·통제 길이·차단 길이·최대 심각도·영향 점수·해제 겹침·매칭률·데이터 지연), 기상, 요일·시각, OSRM 거리·시간·구간 수, 링크·방향 매칭률
- **정답**: `actual_duration_sec`, `actual_delay_sec`, 요청 내 순위, `chosen_best`
- **누수 방지(§6)**: 피처는 출발 전 *수집된* 값만(속도·교통량·돌발은 `collected_at`/`measured_at` ≤ 출발, 기상은 전일), 라벨은 주행 시간대 관측만. 각 피처가 참조한 관측 시각을 컬럼으로 남기고 `scripts/check_route_dataset.py`가 자동 검사한다.
- **생성**: 서울 30 OD쌍 × 관측이 충분한 56개 출발 시각(09/11 17시~09/16 18시) = 1,680요청 3,136행. 전부 라벨 있음(high 2,520 / medium 560 / low 56). 검사 결과 누수 0행, 위반 0건.
- 정의·한계는 `data/processed/route_feature_meta.json`에 기록.

### 3.5 모델 학습과 평가

- XGBoost 회귀(`route_xgb_duration_v1`), 정답 `actual_duration_sec`.
- 채택 기준(§7): 시간순 holdout에서 OSRM 순서 베이스라인 대비 Top-1·regret·MAE가 **모두** 개선될 때만 아티팩트 저장.
- OD holdout(학습에 없는 출발·목적지)을 추가해 새 경로 일반화를 별도 측정.

| holdout | 요청 | 기준 | Top-1 | pairwise | regret | MAE |
|---|---|---|---|---|---|---|
| 시간순 (뒤 30%) | 510 | OSRM 순서 | 55.7% | 55.7% | 271초 | 1,622초 |
| | | **모델** | **88.0%** | **88.0%** | **24초** | **176초** |
| OD (7쌍, 672행) | — | OSRM 순서 | 68.2% | — | 245초 | 1,611초 |
| | | **모델** | **82.5%** | — | **55초** | **200초** |

참고: 데이터셋에서 OSRM 1순위가 실제 1순위와 달랐던 요청이 44%다. 즉 자유속도 기준 최단 경로가 실제로는 절반 가까이 최적이 아니었고, 모델이 그 대부분을 바로잡았다.

### 3.6 서비스 연결 (09/17)

```
요청 → OSRM 후보(≤3) → 휴리스틱 점수(기존) → 경로 모델 ETA 예측
   ├ 후보 전부 자격(링크 매칭 ≥50%, 속도 커버리지 ≥30%)
   │     → ETA 최소 후보 = AI 추천, eta_basis = route_model
   └ 하나라도 미달 / 모델 없음 / 예외
         → 휴리스틱 순위 유지, 해당 후보는 OSRM 시간 + 사유 표시
```

- 온라인 피처는 학습 데이터셋과 **같은 함수**(`candidate_features`)로 만들어 학습·추론 불일치를 막았다.
- 응답에 `predicted_duration_sec`, `eta_source`, `eta_reasons`, `eta_quality`(속도 커버리지·관측 지연·활성 돌발·통제 길이·돌발 데이터 지연)를 포함해 근거와 사용 범위를 드러낸다.
- 화면: 카드 시간은 모델 ETA(`AI ETA` 뱃지) 또는 OSRM(`OSRM 기준` 뱃지). 상세에 AI 예상 시간·OSRM 기본·속도 관측 반영 비율·휴리스틱 점수를 분리 표시. 미적용 시 사유 배너.
- 요청 로그에 예측값·적용 여부를 저장하고, 스케줄러가 출발 90분 뒤 라벨을 자동 생성한다. `evaluate_route_ranking.py`가 휴리스틱 / 모델 ETA / OSRM을 같은 요청으로 비교한다.

실요청(서울역→강남역, 09/17 23시): A 24.7분 / B 24.0분(OSRM 12.4 / 13.1분), 속도 반영 95% / 88%, 관측 4분 전. 휴리스틱은 A, 모델은 B를 선택했다.

## 5. 한계와 정직하게 말해야 할 것

1. **라벨은 실제 주행 기록이 아니다.** 링크 관측 속도로 재구성한 값이며, 모델은 "관측 속도 기준 통행시간"을 맞히도록 학습됐다. MAE 176초는 그 기준의 오차다.
2. **데이터 기간이 짧다.** 09/11~09/16 6일치, 새벽 시간대는 09/16부터. 명절·폭우 등은 학습한 적이 없다.
3. **OD 30쌍**은 서울 주요 간선 위주다. OD holdout에서 일반화는 확인했지만 이면도로·외곽은 관측 자체가 없어 OSRM 시간을 따른다.
4. **교통량 피처는 지점 양방향 합계**다. 측정지점→링크 매핑이 방향을 구분하지 않아 정의서 §3.3의 방향 분리 원칙을 교통량에서는 완전히 지키지 못했다(속도·돌발은 링크 단위라 방향 분리됨).
5. **온라인 검증은 이제 시작**이다. 배포 후 실제 요청에 대한 휴리스틱 / 모델 / OSRM 비교가 쌓여야 운영 기준 개선을 말할 수 있다.
6. 수집 인프라: Render worker가 09/15 16시부터 24시간 가동 중이나 그 전에는 커버리지 29%였다. 데이터셋 출발 시각을 관측이 있는 시간대로 자동 선택해 대응했다.

## 6. 재현 절차

```
# 1) 링크 선형 (표준노드링크 shp + TOPIS 매핑표 필요, 1회)
python scripts/build_link_geometry.py --load-db

# 2) 경로 학습 데이터셋 → 검사 → 학습
python scripts/build_route_training_dataset.py
python scripts/check_route_dataset.py
python scripts/train_route_model.py

# 3) 온라인 비교 (배포 후 라벨이 쌓인 뒤)
python scripts/evaluate_route_ranking.py
```

수집기가 계속 돌면 2)만 다시 돌려 코드 변경 없이 재학습된다.
