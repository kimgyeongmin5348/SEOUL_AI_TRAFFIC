# 경로 추천 문제 정의 09.14

## 1. 문서 목적

현재 RoadPulse의 경로 추천은 **경로 ETA를 예측하는 모델**이 아니라, OSRM이 만든 후보 경로에 교통량 기반 패널티를 더해 후보의 순위를 정하는 방식이다. 이 문서는 현재 방식의 한계와 학습 데이터셋을 변경해야 하는 이유, 변경 후 달성해야 할 목표를 정의한다.

범위는 다음 두 문제를 구분한다.

1. **도로 구간 교통량 예측**: 특정 측정지점·방향·목표시각의 교통량을 예측한다.
2. **경로 추천**: 후보 경로별 예상 통행시간 또는 비용을 비교해 가장 적합한 경로를 선택한다.

현재 학습 데이터셋은 1번에 맞춰져 있지만, 서비스 화면의 핵심 질문은 2번이다. 따라서 교통량 예측 모델을 개선하는 것만으로는 경로 추천 품질이 충분히 개선되지 않는다.

## 2. 현재(09/14) 시스템의 동작

### 입력 데이터

- OSRM 후보 경로 최대 3개
- 후보별 총거리, OSRM 예상 소요시간
- OSRM 구간별 도로명과 구간 소요시간
- RDS의 `traffic_spots` 측정지점 기준정보
- `traffic_volume_measurements`의 지점·방향·차로별 시간 교통량
- `incidents`의 사고·공사·통제·고장 등 실시간 돌발상황
- 기상청 관측소 108번의 기온, 강수량, 습도, 풍속, 기압
- 시각, 요일, 주말, 출퇴근 시간, 측정지점 TM 좌표

### 현재 예측·추천 흐름

1. `traffic_volume_measurements`를 지점·방향·시간별로 차로 합산한다.
2. XGBoost 또는 LightGBM이 시간당 `target_volume`을 예측한다.
3. OSRM 도로명과 교통량 측정지점 도로명을 문자열로 매칭한다.
4. 예측 교통량과 24시간 전 기준 교통량의 증가율을 계산한다.
5. OSRM 시간에 증가율 기반 교통량 패널티를 더한다.
6. 활성 돌발상황을 `link_id`에서 도로명으로 좁힌 뒤, GRS80 TM 좌표를 WGS84로 변환해 OSRM polyline과 150m 이내인지 정밀 필터링한다.
7. 공간 매칭된 사고·공사·통제·고장에 유형별 영향 반경과 예상 해제시각 가중치를 적용한 패널티를 더하고 경로별 돌발 목록을 반환한다.
8. 최근 3시간 이내 도로별 속도 관측으로 OSRM 구간의 양의 지연초를 계산해 속도 패널티를 더한다.
9. 속도 관측 매칭 도로명, 매칭률, 최신 관측 시각을 응답해 미적용 범위를 숨기지 않는다.
10. 경로의 50% 이상 구간이 매칭된 후보 중 점수가 가장 낮은 경로를 AI 추천으로 표시한다.

현재 모델은 `traffic_xgb_baseline_v1`이며, 학습 목표는 `target_volume`이다. 화면의 경로 시간은 모델 결과가 아니라 OSRM 값을 그대로 사용한다.

## 3. 현재 문제점

### 3.1 학습 목표와 서비스 목표가 다르다

현재 모델의 정답은 특정 측정지점의 시간당 차량 수다. 그러나 사용자가 원하는 정답은 다음과 같다.

- 이 경로의 실제 통행시간
- 출발 시각 기준 예상 도착시간
- 다른 후보보다 실제로 빠른지 여부
- 사고·공사·강수·차량 증가를 반영한 경로 비용

차량 수 예측 오차가 작아도 통행시간 순위가 틀릴 수 있다. 반대로 차량 수 예측이 다소 틀려도 후보 간 실제 통행시간 순위를 잘 맞히면 경로 추천에는 유용하다. 현재 데이터셋에는 경로 단위의 정답이 없어 이 차이를 학습하거나 평가할 수 없다.

### 3.2 도로 측정지점과 OSRM 경로의 공간 단위가 다르다

학습 데이터의 한 행은 `spot_id`·방향·시간 단위이고, 추천 입력의 한 행은 OSRM 경로의 도로 구간이다. 현재는 두 단위를 도로명 문자열로 연결한다.

이 방식은 다음 상황에서 취약하다.

- `강변북로`와 `강변북로(성산대교)`처럼 표기명이 다름
- 터널, 램프, 교차로, 진출입로 이름이 다름
- 도로명이 비어 있거나 OSRM과 서울시 표기가 다름
- 같은 도로명이 여러 위치에 존재함
- OSRM 구간과 측정지점이 실제로 어느 거리인지 알 수 없음

매칭 실패 시 실제 교통량이 있어도 `coverage=0`이 되고 AI 추천이 보류된다.

### 3.3 방향과 차로 정보가 추천에 제대로 전달되지 않는다

학습 데이터는 방향 코드와 차로별 교통량을 보유하지만, 추천 단계에서는 OSRM 진행 방향과 서울시 측정 방향을 공간적으로 연결하지 않는다. 현재 구현은 매칭된 측정지점의 양방향 교통량을 합산해 도로 단위 근사값으로 사용한다.

따라서 다음 문제가 생긴다.

- 반대 방향 교통량이 현재 진행 방향 비용에 섞임
- 차로 수와 차로별 차이를 반영하지 못함
- 같은 도로라도 진행 방향·구간별 혼잡 차이를 잃음

### 3.4 속도·통행시간·돌발 데이터가 추천 점수에 빠져 있다

RDS에는 속도와 돌발상황 데이터가 수집된다. 현재 구현에서는 `incidents.link_id`를 `road_segments.road_name`으로 사용해 후보를 좁힌 뒤, 돌발의 GRS80 TM 좌표를 WGS84로 변환해 유형별 영향 반경(사고 180m, 고장 120m, 공사 150m, 통제 250m) 안의 OSRM polyline만 매칭한다. 예상 해제시각이 경로 주행시간과 겹치는 비율도 패널티에 반영한다. 또한 최근 3시간 이내 도로별 속도 관측을 OSRM 구간 거리·시간과 비교해 양의 지연초를 추천 점수에 반영하고, 속도 매칭률과 최신 관측 시각을 응답한다. 원천 데이터에 링크 진행 방향 정보가 없어 진행 방향은 아직 반영하지 않는다.

교통량은 혼잡의 원인 중 하나일 뿐 도로 용량과 현재 속도를 대체하지 못한다. 특히 사고나 통제 상황에서는 차량 수만으로 경로 비용을 설명하기 어렵다.

돌발상황 반영은 단순히 사고 건수를 세는 것으로 끝나면 안 된다. 활성 상태인지, 경로와 실제로 교차하는지, 사고 유형과 영향 범위가 무엇인지, 예상 해제 시각이 출발·도착 시각보다 앞서는지를 함께 판단해야 한다. 그렇지 않으면 이미 해제된 사고나 경로와 무관한 사고가 추천을 잘못 방해할 수 있다.

### 3.5 날씨 피처가 공간적으로 거칠다

전처리 단계에서 기상청 108번 관측소를 우선 선택해 모든 측정지점에 같은 날씨를 조인한다. 서울 전체의 단일 관측소 값은 출발지·경유지·목적지의 국지성 강수나 도로 상태를 설명하지 못한다.

또한 결측 기상값을 선형 보간하거나 중앙값으로 대체한다. 학습 시점에는 보간에 미래 관측값이 사용될 수 있으므로, 실제 온라인 추론 시 사용할 수 없는 정보를 학습 데이터가 보게 되는 미래 정보 누수 여부를 점검해야 한다.

### 3.6 시간 지연과 데이터 공백에 취약하다

서울시 교통량 데이터는 확정·게시 지연이 있다. 현재 시스템은 최신 관측이 현재 시각보다 3시간 이상 늦으면 전체 AI 추천을 중단한다. 수집 스케줄러가 별도 프로세스로 실행되지 않거나 API 수집에 실패하면 다음 현상이 동시에 발생한다.

- AI 미적용
- 예측 반영 범위 미적용
- 사용 학습 모델 사용 불가
- 도로별 예측 교통량 없음

누락된 과거 시각은 최근 30일 같은 시간대 중앙값으로 보완하지만, 이것은 실시간 상태의 대체값일 뿐 실제 관측값이 아니다. 보완 여부와 데이터 신선도를 모델 입력 및 응답에 명시해야 한다.

### 3.7 현재 추천 점수는 ETA가 아니다

현재 점수는 다음과 같이 계산된다.

```text
추천 점수 = OSRM 예상시간
		 + 교통량 패널티
		 + 속도·통행시간 패널티
		 + 활성 돌발상황 패널티
```

돌발상황 패널티는 최소한 다음 정보를 사용해야 한다.

- 사고·공사·통제·고장 등 `incident_type`
- 세부 유형과 심각도
- 유형별 영향 반경과 경로 polyline까지의 거리
- `occurred_at`, `expected_clear_at`과 출발·도착 예정 시각의 겹침
- 경로와 돌발 링크 또는 좌표의 공간적 교차 여부
- 통제처럼 통행 불가인 경우의 큰 패널티 또는 후보 제외

이 점수는 비교용 비용이며, 실제 도착시간 예측값이 아니다. 화면에는 OSRM 기본시간과 돌발·교통량 반영 비용을 구분해 표시해야 한다.

### 3.8 학습·검증 기준이 경로 추천 성능을 측정하지 않는다

현재 모델 평가는 행 단위 교통량 MAE, RMSE, R²다. 이 지표만으로는 다음을 알 수 없다.

- 후보 경로 중 실제 최적 경로를 선택했는가
- 실제 통행시간 순위를 맞혔는가
- 평균 지연시간을 줄였는가
- 추천 불가 판정을 적절히 했는가

따라서 교통량 예측 지표와 별도로 경로 추천 지표가 필요하다.

## 4. Train 데이터셋을 바꿔야 하는 이유

### 핵심 이유

현재 `traffic_training_dataset.csv`는 다음 형태다.

```text
한 행 = 한 측정지점·한 방향·한 시간
정답 = target_volume
```

그러나 경로 추천의 의사결정 단위는 다음이다.

```text
한 행 = 한 후보 경로·한 출발 시각
정답 = 실제 경로 통행시간 또는 경로 비용
```

현재 데이터셋만 유지하면 모델은 차량 수를 잘 맞추도록 최적화될 뿐, 경로 선택을 잘하도록 학습되지 않는다. 또한 도로명 문자열 매칭과 양방향 합산을 추론 단계에서 임의로 수행하므로, 학습 때 본 입력 단위와 서비스가 실제로 평가하는 단위가 다르다.

따라서 기존 데이터셋을 단순히 피처 몇 개 추가하는 방식으로 끝내지 말고, **도로 구간 예측용 데이터셋과 경로 추천용 데이터셋을 분리**해야 한다.

## 5. 변경 목표

### 5.1 1차 목표: 구간 단위 예측 기반 정비

- 교통량, 속도, 통행시간, 돌발, 날씨를 동일한 시간 기준으로 결합한다.
- 활성 돌발상황을 경로 구간과 `link_id` 또는 좌표로 매칭하고, 유형·심각도·영향시간을 피처로 만든다.
- 측정지점 대신 가능하면 `link_id` 또는 좌표 기반 도로 구간을 기본 키로 사용한다.
- 진행 방향을 보존하고 반대 방향을 섞지 않는다.
- 통제·차단처럼 주행 불가능한 돌발은 단순 지연 패널티가 아니라 후보 제외 또는 매우 큰 비용으로 처리한다.
- 미래 시각의 값이 피처에 들어가지 않도록 시간 기준 조인을 보장한다.
- 데이터 신선도, 결측률, 보간 여부를 별도 피처와 품질 컬럼으로 남긴다.
- 기존 `target_volume` 모델과 새 모델을 동일한 시간 분할로 비교한다.

현재 2단계 실험에서는 `traffic_speed_measurements`와 primary `traffic_spot_road_maps`를 결합해 `speed_lag_1h`, `travel_time_lag_1h`, `speed_data_available`을 추가했다. 속도 관측이 있는 학습 행은 전체의 약 0.0855%에 불과했고, 확장 XGBoost의 검증 성능은 RMSE 178.07, MAE 94.32, R² 0.9807로 기존 모델보다 낮아 자동 채택하지 않았다. 속도 수집 범위를 먼저 확대하거나 구간 단위 데이터셋으로 재구성한 뒤 다시 비교해야 한다.

### 5.2 2차 목표: 경로 단위 추천 데이터셋 구축

경로 후보가 실제로 주행된 이력 또는 과거 관측으로 재구성된 경우 다음을 한 행으로 저장한다.

권장 최소 스키마:

| 컬럼 | 의미 |
|---|---|
| `route_request_id` | 하나의 경로 요청 식별자 |
| `route_id` | 후보 경로 식별자 |
| `departure_at` | 출발 예정 시각 |
| `origin_lat`, `origin_lng` | 출발지 |
| `destination_lat`, `destination_lng` | 목적지 |
| `route_distance_m` | 후보 경로 거리 |
| `osrm_duration_sec` | 기준 경로 시간 |
| `segment_count` | 경로 구간 수 |
| `matched_length_ratio` | 실제 도로 데이터가 연결된 거리 비율 |
| `predicted_volume_*` | 경로 구간별 또는 집계 교통량 피처 |
| `speed_*` | 경로 구간 속도 집계 피처 |
| `active_incident_count` | 출발·주행 예정 시간에 활성인 돌발 건수 |
| `accident_count`, `construction_count`, `breakdown_count` | 유형별 활성 돌발 건수 |
| `control_length_m`, `blocked_length_m` | 통제·차단된 경로 길이 |
| `incident_severity_max`, `incident_impact_score` | 최대 심각도와 종합 영향 점수 |
| `incident_clear_overlap_sec` | 예상 해제 시각까지 주행 시간과 겹치는 초 |
| `incident_match_ratio`, `incident_data_age_sec` | 돌발 공간 매칭률과 데이터 지연 |
| `weather_*` | 경로 시공간에 대응하는 날씨 피처 |
| `actual_duration_sec` | 실제 통행시간 정답 |
| `actual_delay_sec` | 기준시간 대비 실제 지연 |
| `route_rank_actual` | 동일 요청 내 실제 순위 |
| `chosen_best` | 실제 최적 경로 여부 |

실제 주행시간을 수집할 수 없다면 1차 대안으로 시간대별 속도·통행시간 관측을 경로 구간에 map-match해 `actual_duration_sec`를 재구성한다. 이 경우 재구성 방식과 품질 등급을 반드시 저장한다.

### 5.3 모델 목표

단계적으로 다음 목표를 검증한다.

1. **구간 교통량 예측**: `target_volume` 또는 `target_speed` 예측
2. **구간 통행시간 예측**: 구간 길이와 속도로 `target_travel_time_sec` 예측
3. **경로 통행시간 예측**: 후보 경로의 `actual_duration_sec` 예측
4. **경로 순위 학습**: 같은 요청의 후보 중 `chosen_best` 또는 실제 순위를 맞춤

최종 서비스 목표는 교통량 숫자 자체의 정확도보다 **동일한 요청 안에서 실제로 더 나은 경로를 선택하는 비율을 높이는 것**이다.

## 6. 데이터셋 구축 원칙

### 시간 누수 방지

- 피처는 반드시 `feature_at` 이전에 관측·수집된 값만 사용한다.
- 목표가 `departure_at` 이후의 통행시간이면, 이후 관측값을 피처에 사용하지 않는다.
- 날씨 보간은 과거값만 사용하는 forward fill 또는 실시간 예보값으로 제한한다.
- 시간순 train/validation/test 분할을 유지하고, 동일한 경로 요청이 여러 분할에 섞이지 않게 한다.

### 공간·방향 정합성

- 도로명은 후보를 좁히는 용도로만 사용하고, 최종 연결은 돌발 좌표와 경로 polyline 거리로 판정한다.
- `link_id`, 측정지점 좌표, 경로 polyline을 활용해 매칭한다.
- 매칭 거리, 매칭 방법, 매칭 신뢰도, 방향 일치 여부를 저장한다.
- 매칭되지 않은 구간은 0으로 채우지 않고 결측 및 미적용으로 구분한다.

### 동일 요청 단위 보존

경로 추천 모델을 학습할 때는 후보 A, B, C가 서로 독립 행이더라도 같은 `route_request_id`를 공유해야 한다. 그래야 모델 평가에서 후보 간 순위와 최적 경로 선택을 계산할 수 있다.

### 데이터 품질 컬럼 보존

각 행에 다음 품질 정보를 남긴다.

- 최신 관측과의 시간 차이
- 사용한 실제 관측값·보완값 비율
- 경로 구간·거리 매칭률
- 방향 일치율
- 기상 관측 시각과 출발 시각의 차이
- 돌발 공간 매칭률, 활성 판정 여부, 돌발 데이터 지연시간
- 사고·속도 데이터의 수집 성공 여부

## 7. 평가 지표

### 구간 예측 모델

- MAE, RMSE, WAPE
- 시간대·요일·도로 유형별 오차
- 최신 데이터 구간에 대한 별도 성능
- 결측 보완 사용 여부별 성능

### 경로 추천 모델

- `Top-1 accuracy`: 실제 최적 경로를 1순위로 선택한 비율
- `Pairwise ranking accuracy`: 두 후보의 실제 순서를 맞힌 비율
- `Regret`: 추천 경로와 실제 최적 경로의 통행시간 차이
- 평균 지연시간 절감
- 추천 불가 판정의 정밀도·재현율
- 매칭률·데이터 신선도별 성능

교통량 RMSE가 개선됐다는 이유만으로 새 경로 추천 모델을 채택하지 않는다. 최소한 시간순 holdout에서 경로 순위 지표와 regret가 함께 개선되어야 한다.

## 8. 권장 전환 단계

### 단계 1: 기존 파이프라인 품질 보정

- 시간대 조인과 미래 정보 누수 검사
- 최신 데이터 기준과 시간대·타임존 통일
- 도로명 매칭 결과와 매칭률 리포트 생성
- 속도·통행시간·돌발 테이블의 사용 가능 컬럼 확인
- 기존 교통량 모델의 최신 holdout 성능 재측정

### 단계 2: 구간 데이터셋 확장

- `link_id` 또는 좌표 기반 매칭 키 추가
- 방향별 속도·통행시간 피처 추가
- 사고·공사·통제 피처 추가
- 돌발 링크·좌표와 경로 polyline 매칭 및 유형별 영향 피처 추가
- 관측 시각, 지연시간, 품질 플래그 추가
- `target_volume`과 함께 `target_speed`, `target_travel_time_sec` 생성
- `active_incident_count`, 유형별 건수, 통제·차단 길이, 심각도, 영향시간 피처 생성
- 사고·공사·통제의 발생·해제 시각을 기준으로 출발 시각과 겹치는 돌발만 포함

현재 1차 링크 데이터셋은 `link_id`별 속도·통행시간을 시간 단위로 집계하고, 연속된 다음 1시간을 `target_speed_kmh`, `target_travel_time_sec` 정답으로 저장한다. 최근 관측 lag, 기상, 링크별 활성 돌발 유형을 함께 보존하며 기상 관측 이전 행과 다음 시각이 연속되지 않은 행은 제외한다. 현재 속도 원천에는 진행 방향 필드가 없어 링크 방향별 분리는 다음 단계로 남긴다.

링크 모델은 기존 교통량 production artifact와 분리해 `scripts/evaluate_link_models.py`로 시간순 holdout만 평가한다. 현재 데이터 기간이 2026-09-10~2026-09-13으로 짧고 방향이 분리되지 않았으므로, 이번 성능 수치는 운영 채택 기준이 아니라 데이터셋 검증용 기준값이다.

### 단계 3: 경로 학습 데이터셋 생성

- 동일 출발·도착 요청에 대해 OSRM 후보 경로를 저장 (09/15: `route_requests`·`route_request_candidates` 테이블로 온라인 요청 축적 시작. 보류 요청도 상태와 함께 저장)
- 후보별 구간 피처를 집계
- 실제 또는 재구성한 `actual_duration_sec`를 연결
- 요청 단위로 실제 순위와 최적 경로 라벨 생성

### 단계 4: 오프라인 비교와 점진적 적용

- 기존 휴리스틱 점수와 새 ETA/순위 모델을 동일한 테스트 요청으로 비교
- 새 모델이 실패하면 기존 방식으로 fallback
- 모델 응답에 예측값뿐 아니라 데이터 품질과 사용 범위를 함께 반환
- 충분한 온라인 평가가 쌓인 뒤 기본 추천 로직으로 전환

## 9. 완료 기준

다음 조건을 모두 만족해야 경로 추천용 데이터셋 변경을 완료한 것으로 본다.

- 경로 후보의 도로 구간이 도로명 문자열만이 아니라 공간·방향 기준으로 매칭된다.
- 출발·주행 예정 시각에 활성인 사고·공사·통제가 경로 구간별로 매칭된다.
- 돌발 유형·심각도·예상 해제시각이 추천 점수와 응답 근거에 반영된다.
- 통제·차단 경로는 명확한 후보 제외 또는 큰 패널티로 처리된다.
- 학습 피처에 미래 관측값이 들어가지 않음이 검증된다.
- 후보별 실제 또는 신뢰도 등급이 있는 통행시간 정답이 존재한다.
- 같은 경로 요청의 후보들을 함께 평가할 수 있다.
- 데이터 지연·결측·매칭률이 사용자와 모델 응답에 표시된다.
- 기존 방식 대비 Top-1 accuracy 또는 regret가 개선된다.
- 실시간 데이터가 부족할 때 AI 추천을 과장하지 않고 명확히 fallback한다.
- 돌발 데이터가 오래되거나 공간 매칭에 실패한 경우 `incident_data_age`와 `incident_match_ratio`를 반환하고, 미반영 상태를 `0건`으로 오해하게 만들지 않는다.

## 10. 결론

현재 데이터셋은 도로 측정지점의 시간당 교통량 예측에는 사용할 수 있지만, 경로 추천의 정답을 직접 학습하기에는 단위와 라벨이 부족하다. 따라서 목표는 기존 데이터셋을 폐기하는 것이 아니라 다음처럼 역할을 나누는 것이다.

- **구간 예측 데이터셋**: 교통량·속도·통행시간의 시계열 예측
- **경로 추천 데이터셋**: 후보 경로별 실제 비용과 순위 학습, 활성 돌발의 유형·영향·해제시간 포함

이 분리를 통해 화면의 `AI 추천`이 단순 교통량 패널티 결과인지, 실제 통행시간과 경로 순위를 근거로 한 추천인지 명확히 검증할 수 있다.
